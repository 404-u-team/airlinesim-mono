# TODO MVP

## Цель MVP

MVP должен дать игроку один законченный игровой цикл управления авиакомпанией:

1. Зарегистрироваться или войти.
2. Создать авиакомпанию и выбрать стартовую базу.
3. Понять состояние компании: деньги, база, флот, доступные возможности.
4. Купить первый самолет.
5. Найти перспективное направление.
6. Создать маршрут и назначить самолет на расписание.
7. Запустить первые рейсы.
8. Увидеть результат в деньгах, событиях, загрузке рейсов и состоянии флота.

Все остальное для MVP вторично. Фондовый рынок, сложный HR, расширенная инфраструктура, полноценная админка и продвинутые события могут оставаться обзорными или закрытыми, если основной цикл выше работает понятно и без ручных обходов.

## Что уже видно во фронтенде сейчас

- Есть shell-приложение с авторизацией, регистрацией, созданием авиакомпании, навигацией, светлой/темной темой и переключением языка.
- Есть базовая карта мира как отдельный MFE, но она пока скорее визуальный слой, а не рабочий инструмент выбора аэропорта, хаба, маршрута или рейса.
- Есть Fleet & Ops с каталогом типов самолетов, фильтрами, покупкой самолета, выбором базового аэропорта и списком купленных бортов.
- Есть Network Planner с подбором направлений и расчетом спроса между аэропортами.
- Есть Finance & Stock с финансовым обзором компании.
- Есть Events & News с лентой событий и счетчиками по severity.
- Есть HR & Facilities с обзором стартовой базы, слотов, совместимых типов и стоимости наземного обслуживания.
- Есть admin-раздел для world data: страны, регионы, аэропорты, связи регионов.

## MVP-чеклист

### 1. Первый вход и создание авиакомпании

- [ ] Игрок может зарегистрироваться, войти и вернуться в игру без потери сессии.

  Для MVP это готово только если пользователь понимает, в каком состоянии он находится: вошел, не вошел, сессия истекла, данные неверные, сервер недоступен. Ошибки должны быть человеческими, а не техническими.

- [ ] После регистрации игрока явно ведут к созданию авиакомпании.

  Форма должна объяснять минимально нужные решения: название, IATA, ICAO, стартовая база. Игрок не должен вводить внутренний ID аэропорта руками. Выбор базы должен быть через понятный поиск по аэропорту, городу, IATA/ICAO и стране.

- [ ] Стартовая база выбирается как продуктовый выбор, а не как техническое поле.

  Для каждого аэропорта в выборе должны быть видны хотя бы город/название, IATA/ICAO, длина ВПП, ночные операции, слоты/пропускная способность и базовые расходы. Игрок должен понимать, почему один аэропорт лучше другого для начала.

- [ ] После создания авиакомпании игрок попадает на понятный стартовый экран.

  Стартовый экран должен отвечать на вопросы: сколько денег есть, где база, есть ли самолеты, что делать дальше. В MVP это может быть Dashboard или Fleet/Network onboarding, но не пустая карта без явного следующего действия.

### 2. Dashboard и общий статус компании

- [ ] Dashboard показывает текущее состояние авиакомпании.

  Минимальный набор: баланс, название авиакомпании, стартовая база, количество самолетов, активные маршруты, рейсы за ближайший период, предупреждения. Статичные цифры в topbar/sidebar не подходят для MVP, если они не отражают реальные данные игрока.

- [ ] Dashboard предлагает следующий лучший шаг.

  Если у игрока нет самолета, главный CTA должен вести к покупке самолета. Если самолет есть, но нет маршрута, CTA должен вести к выбору направления. Если маршрут есть, но нет расписания, CTA должен вести к расписанию. Если рейсы уже идут, CTA должен вести к результатам операций.

- [ ] Вся основная навигация отражает реальный прогресс игрока.

  Игрок должен понимать, какие разделы уже полезны, какие пока пустые из-за отсутствия данных, и что нужно сделать, чтобы они появились. Пустые состояния должны быть продуктово полезными, с действием.

### 3. Карта мира

- [ ] Карта показывает аэропорты, важные для игрока.

  Для MVP минимум: стартовая база, выбранные направления, активные маршруты. Просто глобальная карта без игровых объектов не закрывает пользовательскую задачу.

- [ ] Аэропорты на карте можно осмысленно выбрать.

  При выборе аэропорта игрок должен видеть название, IATA/ICAO, регион, спрос/потенциал, ВПП, слоты, ночные операции и базовые сборы. Отсюда должен быть переход к планированию маршрута или выбору базы, если это онбординг.

- [ ] Карта помогает понять сеть авиакомпании.

  Активные маршруты должны быть видны линиями, а выбранный маршрут должен подсвечиваться. Для MVP достаточно простого отображения без сложной анимации рейсов.

- [ ] Карта не является обязательной блокирующей точкой.

  Все критичные действия MVP должны быть доступны и через списковые/табличные интерфейсы, потому что карта может быть неудобна на маленьких экранах.

### 4. Покупка первого самолета

- [ ] Игрок может выбрать самолет под стартовую базу и бюджет.

  Каталог должен показывать цену, дальность, вместимость, минимальную ВПП, скорость и пригодность для выбранной базы. Неподходящие самолеты должны быть объяснены: слишком короткая ВПП, не хватает денег, нет доступных слотов или другая причина.

- [ ] Перед покупкой игрок видит последствия.

  MVP должен показывать цену покупки, остаток денег после покупки, базу самолета и краткий риск: хватит ли баланса на запуск первых рейсов. Покупка не должна выглядеть как необратимая кнопка без подтверждения.

- [ ] После покупки самолета игрок видит новый актив во флоте.

  В списке должны быть tail number, модель, база, статус, пригодность к полету и следующий рекомендуемый шаг: назначить на маршрут или посмотреть карточку самолета.

- [ ] Карточка самолета готова для MVP.

  Минимум: модель, регистрационный номер, база, статус, вместимость, дальность, техническое состояние, часы/циклы, назначенный маршрут или пустое состояние. Редактирование tail number полезно, но не является обязательным для первого MVP, если номер задается при покупке.

### 5. Планирование маршрута

- [ ] Игрок может найти направление из своей базы.

  Network Planner должен показывать список возможностей из выбранной базы с понятным ранжированием: спрос, дистанция, примерная выручка/потенциал, ограничения аэропортов, совместимость с текущим флотом.

- [ ] Расчет спроса превращается в решение о маршруте.

  После расчета спроса игрок должен видеть не только пассажиров в день, но и ответ: стоит ли открывать маршрут, какой самолет подходит, сколько частот возможно, какие риски есть.

- [ ] Игрок может создать маршрут.

  Для MVP маршрут должен состоять минимум из origin, destination, выбранного самолета или типа самолета, базовой частоты и статуса. Если backend еще не поддерживает полноценные маршруты, во фронтенд-MVP нельзя считать этот пункт готовым: без создания маршрута игровой цикл обрывается.

- [ ] Созданный маршрут появляется в разделе маршрутов и на Dashboard.

  Игрок должен видеть, что решение сохранено, маршрут активен или ожидает расписания, а также что делать дальше.

### 6. Расписание и запуск рейсов

- [ ] Игрок может назначить самолет на маршрут.

  MVP-сценарий должен позволять выбрать купленный самолет, маршрут, дни недели или простую частоту, время вылета и базовый turnaround. Если сложное расписание еще не готово, нужен упрощенный режим: например, "1 рейс в день" или "3 рейса в неделю".

- [ ] Перед запуском расписания показывается проверка ограничений.

  Минимум: самолет подходит по дальности и ВПП, не занят в это время, есть доступные слоты, маршрут не превышает возможности базы, хватает денег на операционные расходы.

- [ ] Игрок может активировать расписание.

  После активации рейсы должны появиться как будущие/запланированные, а маршрут должен перейти в понятный статус. Кнопка запуска должна давать явный результат, а не только менять локальное состояние экрана.

- [ ] Есть экран живых или ближайших рейсов.

  Для MVP достаточно списка: рейс, маршрут, самолет, статус, время, ожидаемая загрузка, ожидаемая выручка/расход. Полноценная real-time симуляция не обязательна, если есть понятное состояние рейсов.

### 7. Деньги и результат операций

- [ ] Финансовый обзор показывает последствия действий игрока.

  После покупки самолета баланс и стоимость флота должны измениться. После запуска рейсов должны появляться выручка, расходы, прибыль/убыток или хотя бы понятная оценка результата.

- [ ] Игрок видит, почему деньги меняются.

  Для MVP нужен простой журнал операций: покупка самолета, расходы на обслуживание/аэропорт, доход от рейсов, другие ключевые транзакции. Без объяснения баланса игрок не сможет доверять симуляции.

- [ ] Финансовый экран дает сигнал риска.

  Минимум: низкий баланс, высокий ежедневный расход, банкротство/риск банкротства, обслуживание флота. Сигнал должен вести к действию: уменьшить расписание, купить другой самолет, открыть более прибыльный маршрут или пополнить капитал, если такая механика есть.

- [ ] Stock market не блокирует MVP.

  Фондовый рынок может быть скрыт, disabled или обзорным до тех пор, пока основной цикл авиакомпании не работает. В MVP он не должен отвлекать от первого маршрута и первых рейсов.

### 8. События, уведомления и обратная связь

- [ ] У игрока есть лента значимых событий.

  Минимум: покупка самолета, создание маршрута, запуск расписания, завершение рейса, финансовое предупреждение, техническое предупреждение. События должны быть связаны с действиями игрока, а не только быть общей агрегированной лентой.

- [ ] Уведомления помогают действовать.

  Каждое важное событие должно иметь понятное действие или переход: открыть самолет, открыть маршрут, посмотреть финансы, исправить проблему. Кнопка "Notify" без реального игрового действия не закрывает MVP.

- [ ] Пустая лента объясняет состояние.

  Если событий нет, экран должен сказать, что происходит: например, "рейсов пока нет, создайте маршрут", а не оставаться пустым.

### 9. База, слоты и инфраструктура

- [ ] Игрок понимает ограничения стартовой базы.

  HR & Facilities уже показывает часть нужных данных. Для MVP этот экран должен объяснять, как база влияет на первый самолет и первые маршруты: ВПП, слоты, ночные операции, сборы, совместимые самолеты.

- [ ] Ограничения базы используются в ключевых решениях.

  Если аэропорт не поддерживает самолет или расписание, это должно быть видно в Fleet, Network Planner и Schedule, а не только на отдельном экране facilities.

- [ ] Расширенная инфраструктура не обязательна для MVP.

  Покупка объектов, найм персонала, обучение, rosters и сложное обслуживание могут быть отложены. Но ограничения базы, влияющие на первый маршрут, должны быть понятны.

### 10. Админка и подготовка мира

- [ ] Админ может подготовить минимальный игровой мир.

  Для MVP достаточно, чтобы через frontend можно было проверить или отредактировать страны, регионы, аэропорты и связи регионов, необходимые для спроса и маршрутов.

- [ ] Игрок не видит админские сущности как часть обычного игрового процесса.

  Admin-раздел должен быть отделен от пользовательского игрового опыта. Если у пользователя нет прав администратора, он не должен упираться в технические CRUD-экраны.

- [ ] Disabled-сущности не воспринимаются как сломанные страницы.

  Все будущие сущности должны быть явно помечены как недоступные/будущие, если они не нужны для MVP. Игроку в обычном режиме такие страницы лучше не показывать.

### 11. Локализация и тексты

- [ ] Все пользовательские тексты MVP доступны на русском и английском.

  Сейчас часть remote-приложений содержит английские строки прямо в UI. Для MVP продуктовые сценарии должны быть полностью понятны на обоих языках: onboarding, ошибки, пустые состояния, CTA, финансовые и операционные статусы.

- [ ] Тексты объясняют игровые решения, а не технические детали.

  Примеры хороших MVP-текстов: "Самолет не подходит: ВПП в аэропорту короче минимальной", "После покупки останется $12,000,000", "Маршрут готов к расписанию". Примеры плохих: raw endpoint error, internal ID, schema field name.

- [ ] Форматы чисел, денег и дат читаются игроком.

  Деньги, пассажиры, проценты, дистанции и время должны быть единообразны. Для MVP особенно важны баланс, цена самолета, спрос, дальность и расписание.

### 12. Адаптивность и доступность игрового цикла

- [ ] Основной MVP-сценарий работает на desktop, tablet и mobile.

  Игрок должен пройти путь от входа до первого рейса без горизонтального overflow, скрытых кнопок и таблиц, которыми невозможно пользоваться на узком экране.

- [ ] Важные действия не доступны только через hover или широкую таблицу.

  Покупка самолета, выбор аэропорта, создание маршрута и запуск расписания должны быть удобны на touch-устройствах.

- [ ] Пустые, loading и error-состояния готовы для каждого ключевого экрана.

  MVP нельзя считать готовым, если при медленном API, пустом флоте, отсутствии маршрутов или ошибке авторизации пользователь остается без понятного следующего шага.

### 13. База знаний и внутренняя документация

- [ ] В продукте есть раздел "База знаний".

  Это должен быть пользовательский раздел внутри приложения, а не только markdown-файлы в репозитории. Пользователь должен находить его из основной навигации, topbar, help-меню или контекстных ссылок на ключевых экранах.

- [ ] База знаний объясняет, как пользоваться системой.

  Для MVP нужны инструкции по основному игровому циклу: регистрация, создание авиакомпании, выбор базы, покупка самолета, поиск маршрута, создание расписания, запуск рейсов, чтение финансов и событий. Документация должна быть написана языком пользователя, без backend endpoint names, DTO, OpenAPI и внутренних ID.

- [ ] База знаний описывает основные игровые понятия.

  Минимум: авиакомпания, стартовая база, аэропорт, ВПП, слоты, самолет, дальность, вместимость, маршрут, спрос, расписание, рейс, загрузка, выручка, расходы, баланс, события, предупреждения. Для каждого понятия должно быть понятно, где оно используется и как влияет на решения игрока.

- [ ] Инструкции связаны с экранами приложения.

  На ключевых экранах должны быть быстрые ссылки на релевантные статьи: Fleet ведет к покупке самолета и статусам флота, Network Planner - к спросу и маршрутам, Finance - к балансу и расходам, Events - к предупреждениям, Facilities - к базе и ограничениям аэропорта.

- [ ] Есть сценарные руководства для новых пользователей.

  Для MVP нужны как минимум статьи: "Первый запуск авиакомпании", "Как выбрать стартовую базу", "Как купить первый самолет", "Как открыть первый маршрут", "Как запустить расписание", "Как понять прибыльность рейса", "Что делать при предупреждениях".

- [ ] Есть справочник ошибок и пустых состояний.

  Пользователь должен понимать, что делать, если нет самолетов, нет маршрутов, не хватает денег, самолет не подходит к аэропорту, нет доступных направлений, сервер недоступен или сессия истекла.

- [ ] База знаний поддерживает поиск и базовую навигацию.

  Минимум для MVP: категории, список статей, поиск по названию/тексту, страница статьи, хлебные крошки или понятный возврат назад. Если полноценный поиск откладывается, должен быть хотя бы структурированный каталог, который покрывает первый игровой цикл.

- [ ] Документация готова на русском и английском.

  Так как приложение поддерживает `ru` и `en`, база знаний тоже должна иметь обе локали или явно согласованную MVP-стратегию. Переключение языка должно показывать соответствующую версию статьи, а не смешивать языки на одной странице.

- [ ] Есть описание самой системы для пользователей.

  База знаний должна объяснять, что это за система, какую роль выполняют основные разделы, как устроен путь пользователя и какие ограничения есть в MVP. Это описание нужно для игроков, операторов, тестировщиков и внутренних пользователей, которые будут оценивать продукт без участия разработчиков.

- [ ] Контент базы знаний поддерживается как продуктовый артефакт.

  Для каждой статьи должен быть владелец или понятный источник правды, дата актуализации или версия, а также правило: при изменении пользовательского сценария обновляется соответствующая статья. Иначе документация быстро перестанет совпадать с продуктом.

## Минимальный Definition of Done для MVP

- [ ] Новый игрок может без помощи разработчика создать авиакомпанию и выбрать стартовую базу.
- [ ] Новый игрок может купить подходящий первый самолет и увидеть его во флоте.
- [ ] Новый игрок может найти направление из своей базы и понять спрос.
- [ ] Новый игрок может создать маршрут.
- [ ] Новый игрок может назначить самолет на маршрут и активировать простое расписание.
- [ ] Новый игрок может увидеть запланированные или выполненные рейсы.
- [ ] Финансы отражают покупку самолета и операционный результат рейсов.
- [ ] События и уведомления отражают ключевые действия игрока.
- [ ] Dashboard показывает реальное состояние компании и следующий шаг.
- [ ] В приложении есть база знаний с инструкциями по основному игровому циклу и описанием системы.
- [ ] Основной сценарий работает на русском и английском.
- [ ] Основной сценарий проходит на desktop и mobile без ручных технических обходов.

## Что можно оставить за пределами MVP

- Полноценный stock market, IPO, shareholdings и trades.
- Сложные loans/leasing, если покупка первого самолета покрывает стартовый сценарий.
- Детальный HR: crew, rosters, training, staff configs.
- Покупка и развитие facilities, если стартовая база уже дает понятные ограничения.
- Продвинутые event actions и event templates.
- Сложное техническое обслуживание, модификаторы самолетов и конфигурации салона.
- Полная анимация рейсов на карте.
- Полная админка всех ERD-сущностей.
