# Модель пассажирского спроса (v2)

> Статус: **проектируется и внедряется** (начато 2026-06-10). Раздел
> [«Статус реализации»](#статус-реализации) отмечает, что уже в коде, а что ещё нет.

## Зачем переписали (проблема «whack-a-mole»)

В v1 один глобальный коэффициент `K` (плюс пара глобальных констант) пытался описать
весь мир. Авиаподвижность (поездок на человека в год) различается между странами в
разы: США летают намного интенсивнее России при том же населении, Россия — интенсивнее
Индии. Когда `K` крутили, чтобы починить одну пару (например, заниженный VKO–AER),
ломались другие (завышался Берлин). Это структурная беда: **глобальная ручка на
неоднородных данных = бесконечная подкрутка**.

Вторая беда — **гранулярность данных**. Спрос кэшировался на backend `RegionLink` по
паре регионов admin1. Население admin1 — это целые земли/штаты (DE-NW = 23 млн,
England = 53 млн), и два аэропорта одной земли (Кёльн CGN и Падерборн PAD оба в DE-NW)
физически делили один и тот же спрос. Отсюда абсурд: Падерборн (~150 тыс. жителей)
получал спрос мегаполиса.

Цель v2 — не «найти правильный `K`», а изменить структуру так, чтобы у параметров было
за что зацепиться в реальных данных, а исключения жили отдельно от физики.

## Принципы

1. **Слои.** Физика (форма) отделена от уровня рынка (масштаб) и от исключений.
2. **Калибруем, а не угадываем.** Там, где есть открытые данные о пассажиропотоках
   (Европа: Eurostat; США: BTS), параметры фитятся. Где данных нет — экстраполируются
   по выученной зависимости, а не задаются вслепую.
3. **Прозрачность.** Любое число можно разложить на множители в UI (и игроку, и
   админу): видно вклад каждого слоя и что именно «игровая ручка», а что — из данных.
4. **Scorecard.** Набор известных пар (модель vs реальность) виден разом, поэтому
   изменение, ломающее знакомую пару, заметно сразу.

## Архитектура и поток данных

```
GeoNames cities ─┐
OurAirports      ├─► [импорт] ─► catchment-население на аэропорт + метро-группы
World Bank       ┘                     │
                                       ▼
              ┌────────────────── РАСЧЁТ СПРОСА (BFF, чистая функция) ──────────────┐
              │ Слой 0  Catchment      население агломерации (город + соседи)        │
              │ Слой 1  Gravity        форма: Pop^α · GDPpc^β · D(distance)          │
              │ Слой 2  Propensity     уровень: множитель страны/направления (фит)   │
              │ Слой 3  Affinity       business / tourism / diaspora (диаспора-данные)│
              │ Слой 4  Overrides      хирургические правки по парам                 │
              └───────────────────────────────┬──────────────────────────────────────┘
                                               ▼
                         demand(metro-pair) ─► split по аэропортам (доля ёмкости)
                                               ▼
                          кэш в BFF SQLite (documents store)  ◄─ калибровка-артефакт
```

### Хранилище (решение)

Спрос **больше не хранится на backend `RegionLink`**. Расчёт и кэш — локально в BFF
SQLite (`frontend/bff/data/game-state/game.db`, существующий `documents` store, см.
`src/db/database.ts`). Это даёт чистую BFF-архитектуру и убирает гранулярность admin1.
Backend Go-сервис в расчёте спроса больше не участвует.

Документы (ключи в `documents`):

- `demand-cache` — рассчитанный спрос по парам (ключ = упорядоченная пара id
  аэропортов или метро-узлов) + версия модели, по которой он посчитан.
- `demand-calibration` — текущий версионированный артефакт калибровки (см. ниже).
- `demand-overrides` — ручные оверрайды по парам.
- `demand-anchors` — закэшированные реальные пассажиропотоки (Eurostat/BTS).

При смене версии модели кэш `demand-cache` инвалидируется (пересчёт по запросу).

## Слой 0 — Catchment (население на уровне города/агломерации)

Вместо населения admin1 каждый аэропорт получает **catchment-население**: сумма
населения близких городов с затуханием по расстоянию.

```text
catchment(airport) = Σ_city  pop(city) · w(dist(airport, city))
w(d) = 1 / (1 + (d / R)^2)          # R ≈ 35 км — радиус «своего» города
учитываем города в пределах ~150 км
```

### Конкурентная аллокация (модель Хаффа)

Наивная сумма «каждый аэропорт берёт всё население в радиусе» задваивает спрос там,
где аэропорты перекрываются: Кёльн и Дюссельдорф (~50 км) оба забирали весь Рейн-Рур,
а крошечный Падерборн — Билефельд/Дортмунд. Поэтому население каждого города
**распределяется** между рыночными узлами в радиусе по доступности:

```text
g_i   = attractiveness_i · w(dist_i)          # привлекательность ≈ ёмкость
share_i = g_i / (G0 + Σ_j g_j)                # G0 — «outside option» (не летят/едут)
catchment_i = Σ_cities pop · share_i
```

`G0` (≈0.12) — доля, которая не достаётся ни одному аэропорту (далеко от всех / не
летят). Метро-группа выступает **одним** узлом-конкурентом, затем её catchment делится
между аэропортами-членами по capacityShare. Результат: Рейн-Рур делится между
CGN/DUS/DTM/FMO, Брешиа (VBS) уходит к Милану, Падерборн схлопывается.

Источник городов — **GeoNames `cities5000`** (все города > 5 000 жителей, с
координатами и населением; CC-BY 4.0). Он уже тянется в пайплайн как `raw.geoCities`
(см. `import/runtime/sources.ts`), отдельный источник добавлять не нужно. Это
естественно решает агломерации: все
московские аэропорты «видят» огромный московский узел и получают ~московское
население, а Падерборн — только своё небольшое.

### Мульти-аэропортные метро (проблема Москвы)

В крупных городах несколько аэропортов обслуживают один рынок (MOW = SVO+DME+VKO+ZIA,
LON = LHR+LGW+STN+LTN+LCY+SEN, NYC, PAR, MIL, TYO…). Если считать спрос для каждого
аэропорта отдельно от полного catchment, рынок города задваивается (× число
аэропортов).

Решение:

1. **Метро-узел** — группа аэропортов с общим catchment. Список метро-кодов IATA
   конечный (~40 городов) и ведётся как curated-таблица; всё остальное — «аэропорт =
   свой метро».
2. Спрос считается **один раз на паре метро** (MOW↔AER), с одним catchment.
3. Затем делится между аэропортами узла **по доле пропускной способности**
   (`max_runway_uses_per_day`, длина ВПП). VKO–AER = доля VKO в рынке MOW–AER.

Это чинит и задвоение, и делает каждый аэропорт меньше рынка всего метро.

## Слой 1 — Gravity (физика, переносится глобально)

Форма спроса — классическая гравитационная модель (Grosche et al. 2007; глобальная
city-pair модель 2018): произведение степенных функций массы и затухание по
расстоянию. Эластичности из литературы (0.6–0.8) и distance impedance калибруются на
данных, но **переносимы между регионами** (это физика, не уровень рынка).

```text
mass = (catchmentA_mln)^α · (catchmentB_mln)^β
     · (GDPpcA_k)^γ · (GDPpcB_k)^δ
G = mass · D(distance)
D(distance) = 1 / (1 + max(distance, 50) / d0)^p
```

Параметры `α, β, γ, δ, d0, p` — результат фита (Слой калибровки), не магические
константы.

## Слой 2 — Propensity (уровень рынка, из данных)

Глобального `K` больше нет. Вместо него — **множитель авиаподвижности на страну** (и,
где нужно, на направление страна→страна), который задаёт абсолютный уровень:

```text
propensity(country) = data-fit, если есть якоря из этой страны
                    = f(GDPpc, островность, плотность ж/д, удалённость), иначе
demand_level = G · sqrt(propensity(countryA) · propensity(countryB))
```

- Для стран с данными (ЕС через Eurostat, США через BTS) propensity фитится напрямую.
- Для остальных — **импутируется регрессией** `propensity ~ f(GDPpc, география)`,
  выученной на странах с данными. Так европейская калибровка обобщается на Азию/Африку,
  а не врёт там.

Здесь же «растворяется» ж/д-конкуренция: Берлин–Кёльн в реальности мал *потому что*
там ICE — фит это просто увидит как низкий уровень страны/коридора. Отдельная физическая
модель поездов не нужна (см. [Слой 4](#слой-4--overrides)).

## Слой 3 — Affinity (business / tourism / diaspora)

`AffinityFactor = a0 + a1·business + a2·tourism + a3·diaspora`.

- **business / tourism** — из региональных scores (как в v1).
- **diaspora — теперь из данных, а не generic-формула расстояния.** Крупные диаспоры
  (например TR↔DE, PL↔DE, MA↔FR, MX↔US) поднимают соответствующие пары. Источник —
  curated-таблица крупных миграционных коридоров (UN Migrant Stock / национальные
  переписи). Это исправляет занижение рынков вроде Берлин–Стамбул.

## Слой 4 — Overrides

Длинный хвост, который не ловит ни одна модель (конкретный ж/д-коридор, политический
запрет, аномальный туризм), задаётся **таблицей оверрайдов** по паре (множитель +
причина). Итог = `модель · override`.

Принципы: оверрайды хранятся **отдельно** от модели (калибровка с ними не дерётся),
они аудируемы списком и показываются в breakdown с пометкой «ручная правка».

Почему ж/д — это оверрайд, а не глобальная функция: ж/д-конкуренция не выводится из
расстояния/страны. Москва–Питер — реально и поезд, и самолёт (иногда самолёт дешевле);
Владивосток — только самолёт; в Европе есть межгосударственные поезда; в США поездов
почти нет. Большая часть этого уже сидит в калиброванном propensity; оверрайдами
добиваются лишь коридоры, заметно отклоняющиеся от нормы своей страны.

## Калибровка

Цель — подобрать параметры физики (Слой 1) и propensity (Слой 2) так, чтобы модель
воспроизводила реальные пассажиропотоки на наборе якорей.

### Якоря (реальные данные)

- **Eurostat `avia_par_*`** — фактические пассажиры по парам аэропортов внутри/между
  странами ЕС, помесячно. Бесплатно, через Eurostat REST/JSON API.
- **US BTS T-100 / DB1B** — пассажиры по парам аэропортов США (и истинный O&D в DB1B).
  Бесплатно, Bureau of Transportation Statistics.

Решение по получению: **тянем вживую по API и сохраняем** в `demand-anchors`. При
последующих запусках используем сохранённое; повторный сетевой запрос только если
включена галочка **refresh**.

### Процедура

1. Подтянуть/прочитать якоря (~300 пар: Европа + США).
2. Зафиксировать форму (Слой 1) и фитить общие эластичности/distance decay по всем
   якорям (это физика, общая глобально).
3. Фитить `propensity` по странам, где якорей достаточно.
4. Регрессией импутировать `propensity` для остального мира по `f(GDPpc, география)`.
5. Сохранить **версионированный артефакт** `demand-calibration`: параметры, дата,
   версия модели, качество фита (R², MAPE), остатки по регионам.

### Scorecard

Отдельная таблица известных пар «модель vs реальность vs % ошибки», доступна в админке
и как тест. После любой калибровки видно все пары разом — это и есть защита от
«починили одно, сломали другое».

### Кнопка в админке

`POST /admin/demand/calibrate` (требует capability `world.manage`):

- `refresh: false` (по умолчанию) — фит по сохранённым якорям.
- `refresh: true` — сперва обновить якоря из Eurostat/BTS API, затем фит.

Возвращает новый артефакт + scorecard. Прозрачность: админ видит, что изменилось,
качество фита и какие пары стали хуже/лучше. Старый артефакт версионируется (откат).

## Прозрачность для пользователя

Endpoint спроса и UI route-planner показывают **полный breakdown**: catchment каждого
конца, gravity, propensity страны, affinity (с разбивкой business/tourism/diaspora),
применённый override (если есть), split-доля аэропорта в метро, и итог. Явно помечается
источник каждого множителя: `data-fit`, `imputed`, `game-knob`, `manual-override`.

## Приложение: историческая модель v1

v1 (один `K = 2.6`, эластичности 0.62/0.55, `DOMESTIC_MULTIPLIER = 1.8`, short-haul
обнуление) описана в истории git этого файла. Её спрос кэшировался на backend
`RegionLink` по паре admin1-регионов — это и есть причина одинакового спроса CGN/PAD и
завышений из-за населения целых земель. v2 заменяет этот путь полностью.
