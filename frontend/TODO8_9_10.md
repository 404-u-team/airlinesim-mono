# TODO8_9_10: События, база и инфраструктура, админка и подготовка мира

Источник: разделы 8, 9 и 10 `TODO_MVP.md`.

Документ составлен по текущему состоянию `frontend/`, `AGENTS.md`, `docs/*`, существующим TODO для разделов 1-7 и текущим BFF/MFE-контрактам.

## Исходные условия

- Разделы 1-7 считаются базовым игровым контуром, на который опирается этот план:
  - у игрока есть сессия и авиакомпания;
  - выбрана стартовая база;
  - можно купить самолет;
  - можно создать маршрут;
  - можно активировать расписание;
  - BFF генерирует рейсы;
  - завершенные рейсы создают финансовые проводки.
- Backend остается источником истины для пользователя, авиакомпании, самолетов и world data.
- BFF-owned overlays остаются источником истины MVP для маршрутов, расписаний, рейсов и операционного ledger.
- Для событий и уведомлений до появления backend Event/Notification endpoints также требуется BFF-owned overlay.
- Покупка объектов, развитие инфраструктуры, найм сотрудников, rosters, training и полноценный event engine не входят в MVP.
- Подготовка мира через admin UI входит в MVP только для стран, регионов, аэропортов, связей регионов и world-data import.
- Все browser-facing запросы идут через BFF.
- Все пользовательские тексты должны существовать на `en` и `ru`.
- Все экраны должны работать на desktop, tablet и mobile без горизонтального overflow.

## Цель объединенного блока

Игрок должен понимать, что произошло после его действий, что требует внимания и как ограничения базы влияют на решения. Администратор должен иметь безопасный, отделенный от игры интерфейс для проверки и подготовки минимального игрового мира.

Объединенный блок заканчивается состоянием, когда:

- покупка самолета, создание маршрута, запуск расписания, завершение рейса и финансовые риски появляются в устойчивой ленте событий;
- важные уведомления имеют реальный переход к проблеме, состояние прочитано/не прочитано и корректный счетчик;
- экран базы объясняет ВПП, ночные операции, слоты, расходы и совместимость;
- одинаковые ограничения используются в Fleet, Network Planner, Schedule, Dashboard и Events;
- обычный игрок не видит и не может открыть admin UI;
- admin может проверить readiness мира, безопасно отредактировать MVP-сущности и запустить dry-run/import.

### Раздел 10: критические разрывы

- Admin-раздел виден каждому вошедшему игроку.
- Shell router не имеет `requiresAdmin` guard.
- Текущий auth/OpenAPI контракт не дает Shell явного признака admin.
- Пользователь без авиакомпании всегда отправляется в onboarding и не может работать как отдельный admin-оператор.
- BFF import endpoints временно не требуют пользовательской авторизации.
- Import mode использует service admin credentials, но запуск не защищен admin-проверкой пользователя.
- Admin CRUD полагается только на backend rejection и не имеет BFF admin boundary.
- Future entities доступны как кликабельные страницы внутри admin, хотя не реализованы.
- Нет общего экрана readiness мира и понятного ответа, достаточно ли данных для первого игрового цикла.
- Import UI ожидает статусы, отличающиеся от реального BFF job contract.
- Import summary показывается как raw JSON.
- После import нет гарантированного сброса world-data cache.
- Admin UI почти полностью hardcoded English.
- Нет тестов admin authorization boundary.

## Обязательные архитектурные решения

### 1. BFF хранит устойчивые события и уведомления

`@airlinesim/event-bus` не является хранилищем. Он используется только для уведомления уже открытых MFE об изменениях, transient toast и навигации.

История событий и состояние уведомлений должны храниться в BFF и изолироваться по `airline_id`.

### 2. Событие и уведомление являются разными сущностями

- Event feed — неизменяемая история значимых фактов.
- Notification — текущее требующее внимания состояние с read/unread и active/resolved lifecycle.
- Один факт может создать event без notification.
- Один длительный риск должен иметь одну deduplicated notification, а не создавать копию при каждом refresh.

### 3. Тексты хранятся как code + parameters

BFF не должен сохранять готовые английские сообщения как источник истины.

UI получает стабильный `code` и безопасные параметры, затем локализует title/body/action на `en` или `ru`.

### 4. Ограничения аэропорта имеют один источник истины

Расчеты ВПП, ночных операций, slot capacity и аэропортовых расходов должны быть вынесены в общий BFF domain/helper слой и использоваться всеми продуктовыми модулями.

UI не дублирует формулы и thresholds.

### 5. Slot capacity MVP не притворяется глобальным рынком слотов

Backend не предоставляет глобальные slot allocations других авиакомпаний.

Поэтому MVP явно показывает:

- физическую дневную capacity аэропорта;
- плановые использования текущей авиакомпании;
- оставшийся planning headroom текущей авиакомпании;
- предупреждение, что это MVP planning model, а не глобально подтвержденный слот.

### 6. Admin security обеспечивается на серверной стороне

Скрытие ссылки в sidebar недостаточно.

До выполнения admin mutation/import BFF обязан подтвердить admin capability текущего пользователя. Нельзя:

- доверять флагу из browser body;
- считать наличие авиакомпании признаком admin;
- давать browser доступ к service admin credentials;
- разрешать import только потому, что BFF настроен с backend admin credentials.

### 7. Явный admin capability contract является блокирующей зависимостью

В текущем OpenAPI нет стабильного `role`/`is_admin`/capabilities контракта.

Для полного Definition of Done требуется один явный источник истины:

- предпочтительно backend identity endpoint с ролями/capabilities;
- допустимо документированное поле JWT claim, если backend гарантирует его контракт;
- временный probe admin-only read endpoint может использоваться только как переходное решение и не считается финальным контрактом.

# Раздел 8. События, уведомления и обратная связь

## Цель раздела

Игрок должен видеть достоверную историю значимых действий и отдельный список проблем, требующих внимания. Любое важное сообщение должно объяснять факт, последствия и доступное действие.

## 8.1. BFF module `events`

- [ ] Добавить `bff/src/modules/events`.

  Предлагаемая структура:

  - `index.ts` — HTTP router;
  - `types.ts` — event/notification contracts и codes;
  - `storage.ts` — atomic persistence;
  - `producer.ts` — запись доменных событий;
  - `notifications.ts` — lifecycle active/resolved/read;
  - `reconcile.ts` — сверка текущих рисков;
  - `snapshot.ts` — загрузка airline/fleet/routes/operations/finance/facilities state;
  - `errors.ts` — normalized error codes.

- [ ] Добавить persistence:

  - `bff/data/game-state/events.json`;
  - `bff/data/game-state/notifications.json`.

- [ ] Использовать те же правила atomic write и corrupt JSON handling, что в routes/operations/finance overlays.

- [ ] Изолировать все чтение и запись по текущему `airline_id`.

  `airline_id` определяется BFF через пользовательский token и не принимается как trusted client input.

### Минимальный event contract

```ts
type StoredGameEvent = {
  id: string;
  airline_id: string;
  code:
    | "AIRCRAFT_PURCHASED"
    | "ROUTE_CREATED"
    | "SCHEDULE_ACTIVATED"
    | "FLIGHT_COMPLETED"
    | "FINANCE_RESULT_RECORDED"
    | "WARNING_RESOLVED";
  category: "fleet" | "finance" | "operations" | "route" | "system";
  severity: "danger" | "info" | "success" | "warning";
  occurred_at: string;
  created_at: string;
  dedupe_key: string;
  source_type: "aircraft" | "flight" | "route" | "schedule" | "system";
  source_id: string;
  target_path: string;
  parameters: Record<string, boolean | number | string>;
  related: {
    aircraft_id?: string;
    flight_id?: string;
    route_id?: string;
    schedule_id?: string;
  };
};
```

### Минимальный notification contract

```ts
type StoredNotification = {
  id: string;
  airline_id: string;
  code:
    | "BANKRUPTCY_FLAG"
    | "BASE_AIRCRAFT_INCOMPATIBLE"
    | "BASE_NIGHT_OPS_CONFLICT"
    | "LOW_BALANCE"
    | "WEEKLY_OPERATING_LOSS"
    | "ROUTE_LOSS"
    | "LOW_MAINTENANCE"
    | "ROUTES_AWAITING_SCHEDULE"
    | "BASE_SLOT_CAPACITY_LOW"
    | "BASE_SLOT_CAPACITY_EXCEEDED"
    | "SCHEDULE_BLOCKED";
  severity: "danger" | "info" | "success" | "warning";
  state: "active" | "resolved";
  is_read: boolean;
  first_seen_at: string;
  last_seen_at: string;
  resolved_at?: string;
  dedupe_key: string;
  target_path: string;
  parameters: Record<string, boolean | number | string>;
  related: {
    aircraft_id?: string;
    route_id?: string;
    schedule_id?: string;
  };
};
```

### Правила хранения

- [ ] `dedupe_key` обязателен для каждого event и notification.
- [ ] Повтор одного mutation response не создает дубликат события.
- [ ] Event после записи не переписывается из-за текущего состояния.
- [ ] Active notification обновляет `last_seen_at` и parameters, но сохраняет `id`.
- [ ] Исчезнувший риск переводится в `resolved`, а не удаляется молча.
- [ ] Resolved notification не учитывается в active/unread count.
- [ ] Read status не должен сбрасываться при обычной сверке неизменившегося риска.
- [ ] Storage имеет разумный retention:
  - events: последние 500-1000 событий на airline для MVP;
  - resolved notifications: последние 100-200;
  - active notifications не удаляются retention-задачей.

## 10.4. World readiness

- [ ] Добавить `GET /admin/world/readiness`.

  Readiness должен отвечать на вопрос: может ли новый игрок пройти первый игровой цикл на текущих данных мира.

### Минимальные readiness checks

- [ ] Countries:
  - есть хотя бы одна страна;
  - ISO заполнен и уникален;
  - tax/permission values валидны;
  - tail code заполнен или явно optional.

- [ ] Regions:
  - есть регионы;
  - каждый регион связан со страной;
  - заполнены population/GDP/tourism/business данные, необходимые demand model.

- [ ] Airports:
  - есть минимум два пригодных аэропорта;
  - каждый аэропорт связан со страной и регионом;
  - есть ICAO/IATA/name/timezone;
  - есть coordinates;
  - есть runway length;
  - есть capacity;
  - есть night operations flag;
  - есть основные fees.

- [ ] Region links:
  - нет self-link;
  - нет duplicate symmetric pairs;
  - ссылки указывают на существующие регионы;
  - affinity values валидны;
  - есть достаточное покрытие для route opportunities;
  - demand cache отсутствует только как warning, если он может быть рассчитан лениво.

- [ ] Product scenario:
  - onboarding airport picker может вернуть варианты;
  - хотя бы один тип самолета совместим хотя бы с одной стартовой базой;
  - из стартовой базы можно получить хотя бы одно route opportunity;
  - facilities overview может быть построен без critical missing data.

### Readiness response

```ts
type WorldReadiness = {
  status: "blocked" | "ready" | "warning";
  checked_at: string;
  counts: {
    countries: number;
    regions: number;
    airports: number;
    region_links: number;
  };
  blockers: ReadinessIssue[];
  warnings: ReadinessIssue[];
  entity_summaries: Record<string, {
    invalid: number;
    missing: number;
    ready: number;
  }>;
  next_actions: Array<{
    code: string;
    target_path: string;
  }>;
};
```

- [ ] Каждый issue должен иметь:
  - stable code;
  - entity type;
  - affected entity id/label, если доступно;
  - user-safe message parameters;
  - target path/filter для исправления.

- [ ] Readiness UI не должен показывать только общий `failed`.
